## Two findings that are NOT 0.2.35 regressions

**1. Ollama was running CPU-only, and the documented fix did not apply.**
`ollama ps` showed `100% CPU`. The gate's documented cause (server started before the
ROCm backend unpacked) was wrong here: a clean restart did not help. The real cause is
that this box's only GPU is an **integrated** AMD Radeon 890M, and Ollama drops iGPUs
unless `OLLAMA_IGPU_ENABLE=1`:

    msg="dropping integrated GPU; to enable, set OLLAMA_IGPU_ENABLE=1"
        id=0 library=ROCm compute=gfx1150 name=ROCm0 type=iGPU

With `OLLAMA_IGPU_ENABLE=1` set before starting the Ollama app, the 890M enumerates as
`library=ROCm compute=gfx1150 type=iGPU total="13.1 GiB"` and every runner reports
`100% GPU`. `test-ollama-gpu-residency` then passes. **This must be set in the
machine's environment permanently, or every future boot returns to CPU-only.**

**SUPERSEDED 2026-11-16 (same day, later).** The dGPU was brought up: the box now has
both an `AMD Radeon(TM) 890M Graphics` (iGPU) and an `AMD Radeon RX 7600 XT` (dGPU,
gfx1102, 16 GiB). With a discrete card present the iGPU flag is now WRONG - it makes
Ollama enumerate three devices (ROCm0 gfx1102, Vulkan1 890M, ROCm1 gfx1150) and the
scheduler can place a runner on the 13 GiB iGPU instead of the 16 GiB card.
`OLLAMA_IGPU_ENABLE` was removed from the User environment and Ollama restarted.
Measured after the change:

    msg="inference compute" library=ROCm compute=gfx1102 name=ROCm0
        description="AMD Radeon RX 7600 XT" type=discrete total="16.0 GiB"
    msg="dropping integrated GPU; to enable, set OLLAMA_IGPU_ENABLE=1"   (x2)

    nemotron-3.5-bolt:e4b-q8_0  1.1 GB  100% GPU  ctx 65536  -> 17.6 s for "Reply with exactly: OK"

17.6 s on the dGPU against 131.7 s on the iGPU for the same prompt. The rule the gate
now records: `OLLAMA_IGPU_ENABLE=1` is correct **only** when the integrated GPU is the
only GPU. On a box with a discrete card, leave it unset.

**2. `test-agent-mcp-e2e` is marginal at its 300 s default on this iGPU.**
A single agent turn here takes 120-520 s depending on load, and the gate default
`-TimeoutSec` is 300. Measured run durations from the `deer-flow` logs:

| Run | Duration | Outcome |
| --- | --- | --- |
| `86c9eb39` | 76 s | success |
| `cd52c8c1` | 74 s | success |

The 520 s run **succeeded**; the gate had simply timed out first. Standalone with a warm

## The two blocked documents: a detector bug, not a data problem

The first pass of this record said the two remaining `blocked` documents "need a human,
not a retry". That was wrong, and the way it was wrong is worth keeping.

Both are `presented-pacgate-ai-平台实战教程` (docx v2 `c2591539`, pdf v1 `91b4011f`),
tenant `9fc20614`, matter `8a3a08ea`. The ledger named `BankAccount "2026-10-26"` as the
surviving structural residue. `2026-10-26` is the document's own date, in YAML
frontmatter and in `数据快照 2026-10-26`.

**Root cause, measured.** `RE_BANK_ACCOUNT_ANCHOR` ended with `[:：\s]*` and the code
then ran `RE_GROUPED_DIGITS.find(rest)` over the **entire remaining text**, so the label
claimed the first digit run anywhere after it:

    anchor '银行账号' at 8520  -> claimed '400-1000'  at 8926  (gap 402 chars)
    anchor '账号'     at 27776 -> claimed '2026-1026' at 28310 (gap 532 chars)

Both are prose in a tutorial. Both passed `bank_account_shape_ok` (8-32 digits once
separators are stripped), so both became `MatchSource::Context` spans - and a Context
span blocks unconditionally in `verify.rs`. The document was permanently unqueryable and
no retry could ever have helped, which is exactly why it looked like a human problem.

**The fix** is the discipline `RE_TH_TAXID_CN` already documents: bound the separator to
whitespace and table punctuation, and require the digit run to start immediately after
it. A legitimate layout leaves the digits at offset 0.

**The `平潭` span was never the blocker.** The same ledger listed
`Location "平潭"` (inside `平潭综合实验区国有资产管理局`, a public body quoted as a
search-result example). `ner.rs` emits only `MatchSource::Model` and `rules.rs` never
emits `EntityType::Location`, so that span was a model guess: recorded in `residue` and
in the notes, never decisive. It disappeared with the same re-sanitize.

**Verified on the live stack, not only in tests:**

| --- | --- | --- | --- | --- |
| docx v2 `c2591539` | `pass` | 73 | `[]` | 4 |
| pdf v1 `91b4011f` | `pass` | 70 | `[]` | 5 |

`kb_chunks` `blocked` 70 -> **0**; both documents are `sanitized` and are returned by

`保定市国资委` are gone from their chunks (0 occurrences each). The dates remain, which
is correct - a document date is not an identifier.

**Deployment.** The fix is not in any published image, so it runs as a locally built
