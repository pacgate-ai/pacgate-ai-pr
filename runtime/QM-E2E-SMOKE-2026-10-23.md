## 3. The two findings

### 3.1 `doc-convert` — host-only failure, not a defect

```
OSError: [WinError 4551] 应用程序控制策略已阻止此文件。
```

`doc-convert` shells out to the `markitdown` CLI. On **this Windows host**,
application-control policy blocks spawning it. That is an artifact of running
the bridge outside its container, not a bridge defect.

Verified the real execution environment is fine:

```
docker run --rm --entrypoint sh ghcr.io/jzkk720/pacgate-sandboxes@sha256:52e867fc… \
  -c "printf 'hello qm e2e' > /tmp/t.txt && markitdown /tmp/t.txt"
  -> hello qm e2e
```

`markitdown 0.1.8` is at `/opt/agent-venv/bin/markitdown` and on PATH, exactly
as `sandbox/Dockerfile` intends. **No action needed.**

### 3.2 The bridge cannot sanitize — a real gap

`pacgate_qm.py` has **no** `sanitize` subcommand:

```
$ grep -i sanitiz pacgate_qm.py
(no matches)
```

But `pacgate-api` has the route, and it works:

```
POST /api/documents/:id/sanitize {"data_level":"T3"}  ->  200
```

**Consequence, observed live.** A document uploaded through QM is `pending`, and
the egress gate correctly refuses to serve it:

```
doc-read -> 409 {"code":"conflict",
  "message":"document is 'pending'; download requires sanitization (or explicit 'never')"}
```

After sanitizing **via the API** (not the bridge), the same `doc-read` succeeded
(34 015 bytes). So the gate is right and the bridge is incomplete: a QM user can
upload a document and then has no way to read it back, because the only path to
`sanitized` is a route the bridge does not expose.

This is a **capability gap, not a security hole** — the fail-closed behaviour is
correct. But it makes `doc-upload` → `doc-read` a dead end from inside QM.

**Suggested fix (not applied — it is upstream's call):** add a `sanitize`
subcommand mirroring the existing `doc-*` commands:

```python
sanitize = subparsers.add_parser("sanitize")
sanitize.add_argument("--document-id", required=True)
sanitize.add_argument("--data-level", required=True, choices=["T1","T2","T3","T4"])
```

and a `sanitize_document(config, document_id, data_level)` that POSTs to
`/api/documents/{id}/sanitize`. Note that T4 will return `chunks_promoted=0` and
stay `pending` by design (plan 028) — the caller then needs the approval
endpoint from 0.2.3, which is a separate decision.
