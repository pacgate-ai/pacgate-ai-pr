# DEFECT — the published 0.2.33 images predate the fix for their own egress gate

**Status:** open upstream. Blocks pinning this stack to `ghcr.io/jzkk720/*:0.2.33`.
**Measured:** 2026-11-09 on this machine, against GHCR and the live database.

## Summary

All six `0.2.33` images were built from `d636174`. That commit contains an egress
query that **cannot succeed**, and the query sits in front of every document read.
Pinning to the published tag turns `/extract` and `/download` into HTTP 500 for
every document — the gate blocks all the traffic it exists to police.

The fix exists in source (`f80693b`) but **no image contains it**.

### The bug

`egress.rs::assert_readable` queried:

```sql
SELECT data_level FROM sanitizer_jobs
WHERE document_id = $1 AND tenant_id = $2
ORDER BY created_at DESC LIMIT 1
```

`sanitizer_jobs` has **no `document_id` column**. Verified against the live database:

```
$ docker exec pacgate-db psql -U pacgate -d pacgate -t -c \
    "SELECT column_name FROM information_schema.columns WHERE table_name='sanitizer_jobs';"
id
tenant_id
matter_id
data_level
mapping_version
mapping
mapping_count
verdict
created_by
created_at
```

It is a **per-matter** table. The per-document link lives in
`redaction_ledger_rows`, which carries both `job_id` and `document_id`:

```
id, job_id, tenant_id, matter_id, document_id, document_version,
input_sha256, output_sha256, redaction_count, verdict, ledger_json, created_at
```

So the query raised `column "document_id" does not exist` on every call, and
`assert_readable` is called by both `extract_document_handler` and
`download_document`. Blast radius: total.

### Why the unit tests missed it

`egress.rs`'s own tests assert `admit(...)` — the **pure decision**. Every one
passed. The SQL that *feeds* that decision was never checked against the schema.
`f80693b` adds a test that asserts the wiring.

## What this machine did instead

Adopted upstream **source** at `c329db8` (which has the fix) and built a local
image layered on the published `0.2.32` image:

```
ghcr.io/jzkk720/pacgate-api:0.2.33-local
```

Layering rather than a full `docker build` for two reasons:

1. The published `0.2.33` image is the broken one — it cannot be the base.
2. `pacgate-ai/Dockerfile` fetches the 406 MB NER weights from `huggingface.co`
   at build time. The `0.2.32` image already carries them, verified by SHA-256
   in the Dockerfile's `ner-model` stage.

Verified: `test-sanitizer-e2e.ps1 -ApiImage ...:0.2.33-local` → **PASS**, 22
checks, including the two that upstream reported failing on the published image
(`extract returned text`, `download allowed post-sanitize`).

## What upstream must do

Either:

- **re-point `v0.2.33`** at a commit at or after `f80693b` and rebuild all six
  images, or
- **tag a `v0.2.34`** from `c329db8` and publish.

Until then `test-release-provenance.ps1` fails, and it is **right** to fail: it
reports 903 image-reachable files changed after the published revision, i.e. a
rebuild from the tag would not reproduce what clients pull.

## Do not

- Do not pin this stack to `ghcr.io/jzkk720/*:0.2.33`. It is a regression.
- Do not "fix" `test-release-provenance.ps1` to pass. It is reporting a real
  defect, not a stale expectation.
